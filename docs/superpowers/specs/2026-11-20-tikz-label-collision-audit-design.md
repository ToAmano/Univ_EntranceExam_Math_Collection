# TikZ 図のラベル重なり監査：設計案

## 目的

TikZ 図の文字同士の重なり・近接を、描画結果から機械的に候補抽出する。LLM と人が確認する図を絞り込み、見落としを減らす。候補は誤りの確定でも、候補ゼロは合格でもない。

## 調査結果

- `scratch/tex_to_md.py` は TikZ ごとに一時 PDF を作り、SVG に変換する。SVG の文字はグリフのパスに変換される例がある。
- `pdftotext -bbox-layout` と `mutool draw -F stext` で、LuaLaTeX が生成した PDF の文字位置を取得できた。数式は複数の文字・行に分かれるため、これを単純にラベルとみなせない。
- Issue #1194 の図を現行 TeX から一時ディレクトリに再生成した。軸上の `1` と `(1+e)/4` は近接するが、文字領域の外接矩形は交差しない。外接矩形の交差だけでは既知の指摘を拾えない。Issue の監査時点と現行 TeX の表示が同じとは限らない。
- 現行の `audit/scan.py` は TikZ の重なりを自動検査対象外とする。図の規約 §11 は PDF 全ページと Web 用 SVG の目視を求める。

## 検出範囲

初版は図内のラベル同士の接触・近接を対象とする。ラベルと線の交差、図の意味・幾何条件、図と本文・caption の関係、Web の実表示は後続の別段階とする。原稿の編集、Issue の自動作成、合否の自動判定はしない。

入力は既存の図生成処理で作る一時 PDF と元の TeX のパス。出力は図番号、ページ、候補位置、距離または交差量、根拠の切り出し画像を持つ JSON と閲覧用 Markdown。コンパイル失敗や文字位置が取得できない図は `unavailable` とし、問題なしとして扱わない。

## 検討した方法

1. **PDF の文字位置を使う（第一候補）**：今の生成経路を利用できる。文字・数式の断片をラベルにまとめる処理が難しく、近接判定には調整が必要。
2. **コンパイル時に TikZ ノードの領域を記録する**：ラベル単位を取りやすい可能性がある。TikZ の各種ノード、マクロ、パス上の `node` に影響せず記録できるか、別途試作が必要。
3. **SVG のパスを解析する**：最終成果物を直接調べられるが、グリフをラベルに戻す情報が乏しく、初版には採用しない。

PDF方式を小さく試し、既知の事例を拾えない、または正常例の誤検出が多い場合にノード記録方式を比較する。距離の閾値は固定値を先に決めず、実例で調整する。誤検出より見落としを減らす方針とする。

実装時の試作では、別々の TikZ ノード `$A$`・`$B$` を PDF 文字抽出器が一つの `AB` に結合した。この条件で PDF 方式は見落とすため、ノード領域を第一候補に変更した。PDF 文字ブロックへの切り替えは `partial` と明記する。これは原稿を変更しない一時コンパイルで行う。

## 検証と導入順

1. Open の #1194・#1458、対応済みの #677・#980 と、正常に見える図を評価用に選び、**現行の描画で実際に指摘が再現するか**を確認する。再現しない Issue は陽性例から外し、履歴として残す。
2. PDF 文字位置の抽出と、ラベルのまとまり・交差・距離の候補判定を一時的な試作で比較する。候補の切り出し画像を人が確認し、既知の陽性を拾う率と正常例の候補数を記録する。
3. 足りない場合だけ、TeXを変更せず一時コピーのコンパイルでノード領域を記録する方法を試す。PDF方式との結果を比較して実装方式を選ぶ。
4. 選んだ方式を read-only の CLI として `audit/` に追加する。`audit/visual_prepare.py` のパケット形式への統合は、単独CLIの精度と実行時間を確認した後に判断する。
5. PDF 全ページと Web 用 SVG の目視を最終確認として維持し、監査の説明に自動候補の限界を明記する。

## 完了条件

評価用の陽性例・正常例ごとに検出結果と誤検出を報告できること。候補には再確認に使える位置と画像があること。対象図をコンパイルできない場合や文字抽出に失敗した場合は明示されること。元の TeX と既存の成果物を変更しないこと。
